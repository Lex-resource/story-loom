# V9 跨系统时间证据闸门

## 元数据

- 父版本：V8
- 修改假设：V8 的统一证据对象已降低身份、能力和物品状态升级，但模型仍把未校准时钟的数值差异写成“广播前后”，导致第 2 章连续性重试上限暂停。
- 研究目标：只增加跨系统时间的确定性语言约束，不增加模型调用，不改变 V8 证据对象和紧凑交接格式。

## 具体变更

1. Planner、Writer、Editor、Validator、Extractor 增加 V9 时间证据闸门。
2. 未校准时间源只能写成“分别显示”“数值差异”“待比对”，不能写成实际之前/之后、早于/晚于、先后或因果。
3. Validator 将无限定的跨系统时间顺序视为硬连续性问题；Editor 优先改成中性显示值。
4. 疑问句不得预设记录存在主动推送者、创建者或操作者。

## 验证方式

使用独立项目、同一 OpenAI provider、备用 provider 关闭，连续生成 10 章。V8 的两章部分运行只作为父版本诊断，不与 V9 共享项目、正文或记忆。

## 预期验收

- 时间线类内容重试相较 V8 明显下降。
- 不新增模型调用；记忆上下文平均保持 V8 的紧凑水平。
- 七维平均和连续性门槛不低于 V8。

## 质量与失败模式

V9 的时间证据闸门确实捕获了第 4 章的一处跨章时间冲突：上一章已经宣布二十分钟核查权限到期，本章却把权限写成尚未结束。Validator 给出了“改为已到期但终端保留最后只读页面”的确定性修复建议。其他内容重试主要是暂停流程与已排队请求的因果衔接、文件提交状态的语义边界、页面显示文本与后台实际操作的混淆，以及接管提示被写成已开始倒数。说明时间闸门开始工作，但它没有消除连续性重试。

第 4 章暴露出比提示词更基础的实验问题：Validator 达到暂停条件后，后续恢复/发布没有写出同一章的最终完成事件。数据库状态和正文可以是最终发布状态，事件审计却只能看到暂停阶段。下一轮必须先让“暂停、恢复、重写、人工发布、Extractor 完成”共享一个按章节幂等的最终状态记录，并增加对应的真实流程回归测试。

## V9 结论

从已记录质量看，V9 达到了七维评分、连续性和伏笔兑现门槛；从重试目标看，平均内容重试虽为 `0.80`，但零重试率仅 `60%`，未达到验收条件。从实验方法看，第 4 章最终完成事件缺失，使十章的最终调用成本、最终质量和硬冲突零值无法完整审计。因此 V9 是有效的诊断样本，不是可以直接选为最终版本的完整通过样本。

V10 的优先级应为：先修复章节完成事件的生命周期绑定并用单章暂停/恢复/发布烟测验证，再在相同 V9 提示词上重跑一组完整十章；只有事件链完整后，才有意义继续比较新的提示词改动。
